# Setting up SevaOne on a new machine

For whichever agent (Claude, Codex, or a human) is bringing this stack up somewhere it has
never run before — a second office laptop, a fresh VM, etc. Read [`AGENTS.md`](../AGENTS.md)
and [`SESSION_HANDOFF.md`](../SESSION_HANDOFF.md) first for the standing project decisions and
current architecture; this doc only covers the mechanics of getting a first working copy of the
stack running on a machine that doesn't have one yet.

## The two tracks: code vs. secrets

Everything in this repo (`git clone`/`git pull`) gets you the code, the Dockerfiles, the SQL
migrations, and the systemd *unit files* for the GPU tunnels. It deliberately does **not** get
you any real secret — `.gitignore` excludes `.env`, `*.pem`, `*.key`, `secrets/`/`docs/secrets/keys/`, and
`credentials*.json` on purpose, and that boundary should never be crossed by committing a real
secret into git, even to make onboarding a new machine faster. Git history is permanent and
shared with everyone who has repo access; a secret committed once has to be treated as
compromised and rotated, not just deleted from a later commit.

So secrets travel a **separate, out-of-band path**: copy them directly from a machine that
already has them, over SSH, never through git.

```bash
# From the machine that already has the secrets (adjust user@host and destination path):
scp -r /home/srikanth/Desktop/sevaone/Secrets  newuser@new-laptop:/home/newuser/Desktop/sevaone/
scp /home/srikanth/Desktop/sevaone/docker-deploy/.env newuser@new-laptop:/home/newuser/Desktop/sevaone/docker-deploy/.env
```

(`rsync -av` works the same way if you prefer it; an encrypted archive handed over on a USB
drive is fine too. What matters is that the transfer never passes through git, email, chat, or
any other place the content could linger or be re-shared unintentionally.)

### What's actually in `docs/secrets/keys/`

As of this writing, `docs/secrets/keys/` holds:

- `sevaone-gpu-tunnel.pem` — the SSH private key for all three GPU-box tunnels (see below).
- `srikanth-sevaone.rove-lungfish.ts.net.crt` / `.key` — the TLS cert/key the shared `nginx`
  service serves on.
- `sevaone-dev.crt` / `sevaone-dev.key` — a secondary/dev cert pair.
- `ai-monitor.key` — the API key the `bff` container presents to the `ai-monitor` GPU-host
  telemetry sidecar (mounted into `bff` at `/run/secrets/ai-monitor.key`).
- `CeG_DigiLocker_Test_Credentials.txt`, `dept-integration-test-credentials.md`,
  `Department_Integration_Test_Credentials.docx`, `otp message sample code.txt` — reference
  material for the DigiLocker/department integration secrets that go into `.env` (see below).
- `ssh-key (3).pem` — check with whoever set this up before assuming it's still needed; it isn't
  referenced by any tracked systemd unit or compose file today.

Copy the whole directory rather than picking files individually — it's small, and a missing file
here just means the tunnel or nginx container using it will fail to start with a clear error
mentioning that exact path.

### What actually needs to be in `docker-deploy/.env`

`docker-deploy/scripts/setup-stack.sh` checks this for you and will refuse to continue with a
clear list of anything missing, so you don't have to guess — just run it and follow what it
prints. For reference, the variables it looks for:

- `DIGILOCKER_DEPT_KEY`, `DIGILOCKER_HMAC_KEY` — **must be copied over manually**, real
  DigiLocker department secrets. These are not regenerated by anything.
- `WSO2_CITIZEN_ISSUER_CLIENT_ID` / `_SECRET`, `WSO2_OPERATOR_ISSUER_CLIENT_ID` / `_SECRET`,
  `WSO2_GOVADMIN_ISSUER_CLIENT_ID` / `_SECRET`, `WSO2_CITIZEN_ISSUER_SIGNING_KEY_PEM` — these
  only need to resolve to *some* value before the script runs (a placeholder is fine); the
  script's own WSO2 provisioning step overwrites them with freshly generated real ones on this
  machine. Copying the old machine's values over is harmless but unnecessary.
- `AI_MONITOR_API_KEY` / `AI_MONITOR_URL` — optional; leave empty to skip GPU telemetry, or set
  `AI_MONITOR_URL=http://host.docker.internal:8010` once the `ai-monitor` tunnel (below) is up.
  The API key itself is normally supplied via the mounted `docs/secrets/keys/ai-monitor.key` file instead
  (`AiMonitor__ApiKeyFile` in `bff-config/appsettings.Docker.json`), so this var can usually stay
  empty.
- `MOBILE_SEVA_SMS_*` (five vars) — optional; empty falls back to a logged/no-op SMS sender, see
  `SevaOne.Infrastructure/DependencyInjection.cs`.

Easiest path: copy the old machine's `.env` wholesale (as shown above) and let `setup-stack.sh`
regenerate the WSO2 values on top of it.

## AI connectivity

All AI runs on the shared GPU server (`101.53.138.83`) and never in this stack. The stack has two
kinds of AI connection:

| Service | How it is reached | Used by |
| --- | --- | --- |
| `sevaone-rag` (port 8000) | Directly, `http://101.53.138.83:8000`. No tunnel. | SevaOne `bff` (`AiBackend:BaseUrl`), the SevaOne `frontend` proxy (`/rag-api/`), and the Seva-Sindhu-One backend (`AI_BACKEND_URL`) |
| `ai-monitor` (port 8010, loopback on the GPU host) | SSH tunnel to `172.17.0.1:8010` | `bff` `AiMonitor__BaseUrl`, the Superadmin AI status view |
| `ai-admin` government assistant (port 8090, loopback on the GPU host) | SSH tunnel to `172.17.0.1:8090` | `bff` `GovAdminAiAssistant__BaseUrl` |

The earlier co-developed `ai_backend` is retired, so the old `sevaone-gpu-tunnel` (8000) and
`sevaone-rag-gpu-tunnel` (8009) units are no longer needed and can be disabled.

Each tunnel is a systemd unit with `Restart=always` (never a bare backgrounded `ssh`). The unit files are
in `apps/Artificial-Intelligence/ai-monitor/deploy/systemd/` and `apps/Artificial-Intelligence/ai-admin/deploy/systemd/`.
Edit each unit's `User=` line and the `/home/...` key and `known_hosts` paths for the new machine. The key is
`docs/secrets/keys/sevaone-gpu-tunnel.pem`; existing units that still use `Secrets/...` keep working through
the git-ignored `Secrets` symlink at the repository root. Installing a unit is a system change and needs sudo:

```bash
sudo cp <path-to-unit-file> /etc/systemd/system/<same-filename>
sudo systemctl daemon-reload
sudo systemctl enable --now <same-filename-without-.service-suffix>
```

Check that the AI service is reachable and the tunnels are up:

```bash
curl -sS http://101.53.138.83:8000/health
systemctl status sevaone-ai-monitor-tunnel.service --no-pager
curl -sS -H "X-Monitor-Key: $(cat docs/secrets/keys/ai-monitor.key)" http://172.17.0.1:8010/metrics
```

`ai-admin` must be deployed on the GPU host before its tunnel has anything to reach. At the time of writing
it is not: the host has no `/opt/sevaone/gov-admin-ai` and no supervisor program for it, so the government
assistant answers with an error until it is deployed.

## Bringing up the stack

Once `docs/secrets/keys/` and `docker-deploy/.env` are in place:

```bash
cd docker-deploy
./scripts/setup-stack.sh
```

The script starts Postgres, Redis and Kafka, the WSO2 databases, WSO2 Identity Server and API Manager, the
Flyway migrations, and the apps: `bff`, `frontend`, `admin-panel`, `sevasindhu-backend`, `sevasindhu-frontend`
and the shared `nginx`. It does not start the legacy dashboard or any AI service. The SevaOne portal is on
port `80`, the admin panel on `5096` and the Seva-Sindhu-One frontend on `5095`. Stop it with
`./scripts/stop-stack.sh`.

## Verifying AI end to end

1. Citizen AI Discovery chat in the main `frontend` (port 80) should return a real answer, not a 502.
2. The Seva-Sindhu-One chat (port 5095) should do the same.
3. Admin panel, AI Operations (Superadmin only, port 5096) should show the monitor as reachable. The
   government assistant works only once `ai-admin` is deployed on the GPU host.
