Reviewed: `SevaOne_ServicePlus_Replacement_Phase1_Functional.pptx` (94 slides).
How: read the full extracted text of all 94 slides (word counts, repeated phrases), read the full
text of modules 1, 2, 7 and 11 and the HANDOFF/DECISIONS files, and looked at the rendered slides
1, 3 and 43. I did not read every slide line by line, so the examples below are samples. Apply
each rule to all slides.

Codex: do not edit this file. Work from it and record what you changed in HANDOFF.md.

## Verdict

Structure, honesty labels and visuals are good. The flows are clear and the unDraw pictures work.
**The wording is the problem.** It reads like a specification written by a consultant, not
something a department officer aged 55 or more will follow in one reading. The owner's
requirement is plain, local English: "this is what ServicePlus has, this is what we propose, and
these are the cautions."

Measured on the current text:
- About 82 words per slide on average, up to 101. Too dense for a slide people read on a screen.
- Heavy words repeated: "responsibilities" (37 times), "departmental" (30), "replacement" (25),
  "confirmation" (21), "alternative" (20), "implementation" (19), "established" (18).
- The phrase "Known evidence boundary" appears on 43 slides. "Artwork: unDraw" appears on 91.
  "Functional choice" and "Alternative rejected" appear 20 times each.

## 1. Write for a reader who is not a technical person

Rules:
- Short sentences. Aim for 12 words or fewer. One idea per sentence.
- Everyday words. If a word is not used in a normal office conversation, replace it.
- Say who does what: "The officer checks the form", not "Review is performed".
- No labels that only we understand. A reader should never need us to explain a heading.
- Slides carry the main point; long explanations go to a notes file, not the slide.
- Aim for 40 to 50 words per slide at most. Split a slide rather than shrink the text.
- Keep Known / Proposed labels (they matter) but write them in plain words, see section 3.

Examples of rewrites (apply the same style everywhere):

| Now | Write instead |
|---|---|
| Account policies requiring confirmation | Things we still need the department to decide |
| Known evidence boundary | What we do not know yet |
| Open policies and evidence boundaries | Questions to settle with the department |
| Existing capability and evidence | What ServicePlus has today |
| Proposed functional responsibilities | What the new system will do |
| Proposed operating flow and choice | How it will work, step by step |
| Source-based capability: Listed features do not prove the current Karnataka deployment | These are features NIC says it has. We have not seen them working in Karnataka. |
| The client inventory records login and returned role information | The mobile app logs the user in and gets back the user's role |
| Official activates and signs in | The officer turns on the account and logs in |
| Authoritative directories | Official lists of offices and areas |
| Reconcile gateway and treasury records against application-linked collections | Match the bank and treasury records with the payments we recorded |
| Keep amount due, payment attempt, confirmed receipt and settlement distinct | Keep four things separate: the amount to pay, the payment tried, the receipt, and the money received |
| A browser return or citizen screenshot cannot alone establish confirmed payment | A screenshot or the browser coming back is not proof of payment |
| Alternative rejected: A hardcoded processing chain for every service | We chose not to build a fixed set of steps separately for every service |
| Shared workflow capabilities with explicit service-kind behaviour | One common way of working for all services, with clear rules for each of the three kinds |
| Identity linking | Using one account for citizen and officer work |
| Attributable | Shows who did it |

Word swaps (use the plain word everywhere):

| Avoid | Use |
|---|---|
| responsibilities | work / duties / what it does |
| authoritative | official |
| organization (also spell "organisation" the Indian way consistently) | office structure |
| eligibility | who can apply |
| reconciliation | matching the records |
| revalidation | checking again |
| provenance | where the data came from |
| attributable | shows who did it |
| lifecycle | stages from start to end |
| tenant | state (and its departments) |
| workspace | the person's own screen / page |
| concurrent / fork and merge | work done in parallel / split and join |
| exception queue | list of problem cases |
| disbursement | payment of benefit money |
| jurisdiction | the area an office looks after |
| pinned version | the version that was in force when the application was made |
| client inventory / API inventory | the mobile app (do not mention the API list on slides) |
| established / unconfirmed | proved / not confirmed |
| service-kind | type of service |

If a technical word is needed (for example "tenant" for the multi-state idea), explain it once
in plain words the first time and keep a one-slide glossary near the end.

## 2. Use the three-part story the owner asked for

Each module should read as three things in this order, with these exact plain headings:

1. **What ServicePlus has today.** Two or three short points.
2. **What we propose.** The new way, in a flow with the unDraw pictures.
3. **Things to be careful about.** The cautions, the things not yet decided, and what we are
   not sure of. Say which ones the department must decide.

Today the deck has evidence, then open questions, then responsibilities, then a flow and a choice.
The content is right but the order and the names hide the three-part story. Keep the content,
rename and reorder to the three parts above. The "choice and rejected alternative" can stay as
one short line inside "What we propose", written plainly (see the table above).

## 3. Honesty labels in plain words

Keep the labels (this protects us), but use plain words and put them in one place:
- **Known** becomes "NIC says" (and the slide number).
- **Assumed** becomes "We think".
- **Proposed** becomes "We propose".
- "Not disclosed" becomes "NIC has not told us".

Remove "Artwork: unDraw" and "Art: unDraw" from every slide footer. unDraw needs no credit. Put one
line on the last slide if the owner wants a credit. This also frees the footer for the source.

## 4. Specific issues to fix

1. **Footers are too long and too technical** (for example slide 1 footer, slide 43 footer). Keep
   one short line: "Source: NIC deck, slides 5 and 7".
2. **Titles that repeat.** Every module uses "Existing capability and evidence", "Open policies and
   evidence boundaries", "Proposed functional responsibilities". A reader cannot tell modules
   apart by the titles. Use titles that say the point, for example "How a citizen gets an
   account" or "How payments are matched".
3. **Slides 5 and 10 and similar:** side notes like "Prior actions remain attributable after an
   account closes" should become "Even after an account is closed, we still show who did what."
4. **Sentences that start with "Proposed ... expressed as business responsibilities and
   outcomes".** Delete these sub-headings. They explain the deck to us, not the topic to the
   reader.
5. **Too many slides per module?** Four per module is fine. 94 in total is long for the audience.
   Consider a short main deck (about 30 slides: one summary slide per module plus the overall
   journeys) with the detailed four-slide treatment as an appendix. Owner to decide.
6. **Slide 3 and the flow slides look good.** Keep that style. Labels under the pictures can be
   shorter ("Create account", "Check phone or email", "Switch on account", "Log in", "Your page").

# REVISION REQUEST 2 (owner decision, 18 October 2026): new deck structure. Supersedes Request 1.

The owner rejected the 37-slide version. This is the new structure. The 30 to 40 slide limit no
longer applies; use as many slides as the content needs, but keep each slide light.

## What was wrong with the 37-slide version (Claude's review)
1. **The module slides were cut down to fragments.** "Keep past actions", "Admin adds officers",
   "Login choices". A reader cannot tell what they mean. Plain English means short, complete,
   clear sentences, not two-word labels. The earlier word limit was meant to stop crowding, not to
   remove meaning. Use whole sentences of about 8 to 14 words.
2. **No diagrams.** Slide 3 is a list of words in five columns. Module slides are three text
   columns with a small unDraw picture floating at the top and a large empty gap.
3. **The pictures are too small and detached.** An illustration should sit beside the idea it shows
   and be big enough to read.
4. **The story is missing.** The owner wants to understand the whole system first, then the life of
   a citizen and an application, and only then each module.

## New order of the deck

### Part A. The whole of ServicePlus, as pictures (overview functional flow)
Draw how everything fits together. Every slide is a diagram with steps and arrows plus unDraw
pictures. Each box or step has a short plain sentence under it. Suggested slides:
1. **The big picture.** Who uses it, how they reach it, what runs inside, and what it connects to,
   on one diagram.
2. **Who uses ServicePlus.** Citizen, assisted operator, officer, department administrator, service
   owner, platform administrator: one picture each with one line on what they do.
3. **How a service is set up and put live.** Service owner designs form, steps, documents and
   messages, tests it, publishes it, then officers and offices are given access.
4. **How an application travels from start to finish.** Citizen fills form, submits, goes to the
   right office, officer decides, certificate or rejection reaches the citizen.
5. **Three types of service.** Done inside the system, collection only, handed to a department's
   own site. Show each as its own path on one diagram.
6. **What supports every application.** Payments, documents, messages, connections to other
   systems, reports, appeals, history of who did what. Show where each one touches the journey.
7. **One system for many states** (multi-tenancy) in a simple picture.
8. **Moving Karnataka's existing services and applications** in a simple picture.

### Part B. Lifecycles (one diagram each, with the states or stages named)
Start with the two the owner named, then the others.
1. **Citizen lifecycle.** From first visit and creating an account, through finding a service,
   applying, paying, being asked to correct something, getting the result, downloading the
   certificate, and complaining or appealing if needed.
2. **Application form lifecycle.** Owner confirmed: this is the life of a citizen's application:
   draft, submitted, with the officer, correction asked, resubmitted, approved, rejected,
   certificate issued, closed. The life of the form design itself (built, tested, published,
   changed, retired) goes under the service lifecycle in item 3.
3. **Other lifecycles:** service (design, test, publish, change, retire), officer account and
   posting, payment (due, tried, paid, failed, refunded, matched), certificate (made, signed,
   issued, checked, cancelled), complaint and appeal, message (sent, delivered, failed, retried),
   state or department joining the platform, and moving Karnataka's data over.
For each lifecycle show: the stages in order, who moves it to the next stage, and what can go
wrong or send it back. Mark what ServicePlus does today ("NIC says") and what we add ("We propose")
on the same diagram using two colours and a key.

### Part C. The 20 modules (layout decided by the owner: three slides per module, about 60)
Build Part C after Parts A and B are reviewed. Each module gets three slides, each with a diagram
and unDraw pictures, in this order:
1. **What ServicePlus has today.** A picture-led diagram of how this module works in ServicePlus,
   with whole plain sentences. Mark each point "NIC says" with the source slide, or "NIC has not
   told us" where the source is silent.
2. **What we propose.** A diagram of how the module will work in the new system, with whole plain
   sentences. Mark "We propose". Show what is new or different compared with slide 1.
3. **Things to be careful about.** The cautions, what is not yet decided, and what the department
   must decide. Show them as a simple diagram or checklist picture, not a bare list.
Slide titles say the point (for example "How a citizen gets an account"), not the template name.
Keep modules in order 1 to 20 under the five group names. The three-slide layout replaces the
three-column layout used in the 37-slide version.

## Rules for every slide in Parts A and B
- Diagram first. Use native shapes and arrows, with an unDraw picture beside each key step.
- Pictures at a size where the owner can see what they show. No picture left floating in a corner.
- Whole, plain sentences. Never a bare two-word fragment as the only explanation.
- No big empty areas. Fill the slide with the diagram, or reduce the slide.
- No technical words. No technology names. Hosting stays open.
- Keep the plain labels ("NIC says", "We think", "We propose", "NIC has not told us") and the
  source slide numbers. Do not invent ServicePlus facts. Action codes 9/10/11 stay "not confirmed".
- Use `sources/ServicePlus_Detailed_Analysis.docx` and `sources/ServicePlus_PPT.pptx`.
